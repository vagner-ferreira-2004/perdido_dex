
# Contexto de Desenvolvimento — Lost and Found

## 1. Objetivo

Este documento define as convenções gerais de desenvolvimento do projeto **Lost and Found**, um web app de Achados e Perdidos desenvolvido inicialmente para a faculdade.

O objetivo deste contexto é manter o projeto consistente entre os desenvolvedores, principalmente em relação a:

* nomenclatura;
* organização do código;
* banco de dados;
* migrations;
* modelagem DBML;
* regras de negócio;
* idioma utilizado no código.

### Regra principal

A **documentação e as explicações podem ser escritas em português**, para facilitar a compreensão de todos os desenvolvedores.

Porém, **todo identificador e elemento estrutural do código deve ser escrito em inglês**.

Isso inclui:

* variáveis;
* funções;
* classes;
* arquivos;
* pastas;
* tabelas;
* colunas;
* rotas;
* controllers;
* services;
* models;
* schemas;
* DTOs;
* migrations;
* constantes;
* endpoints;
* nomes de campos da API.

---

# 2. Padronização de nomenclatura

## 2.1 Variáveis

Variáveis devem utilizar `snake_case`.

```python
user_name = "John"
object_found = getObject()
found_date = datetime.now()
```

Evitar:

```python
userName = "John"
nome_usuario = "John"
```

Preferir:

```python
user_name = "John"
```

---

## 2.2 Funções

Funções devem utilizar `camelCase`.

```python
def getUserById(user_id):
    pass

def createObjectFound(data):
    pass

def updateObjectStatus(object_id, status):
    pass
```

Evitar:

```python
def get_user_by_id(user_id):
    pass

def buscarObjeto(objeto_id):
    pass
```

---

## 2.3 Classes

Classes devem utilizar `PascalCase`.

```python
class User:
    pass

class ObjectFound:
    pass

class Location:
    pass
```

---

## 2.4 Arquivos

Arquivos gerais devem utilizar `PascalCase`.

```text
User.py
ObjectFound.py
Category.py
Location.py
Characteristic.py
Photo.py
Pickup.py
```

### Exceção: Routes

Arquivos de rotas devem ser escritos em minúsculo.

```text
routes/user.py
routes/object.py
routes/category.py
routes/location.py
```

### Exceção: Controllers

Arquivos de controllers também devem ser escritos em minúsculo.

```text
controllers/user.py
controllers/object.py
controllers/category.py
controllers/location.py
```

---

## 2.5 Constantes

Constantes devem utilizar `UPPER_SNAKE_CASE`.

```python
MAX_FILE_SIZE = 5 * 1024 * 1024
DEFAULT_OBJECT_STATUS = "AVAILABLE"
```

# 3. Idioma do projeto

Existe uma separação entre **documentação** e **código**.

### Documentação

Pode ser escrita em português.

Exemplo:

```python
# Busca o objeto pelo identificador informado
def getObjectById(object_id):
    ...
```

Isso permite que desenvolvedores que não possuem domínio avançado de inglês compreendam o funcionamento do código.

### Código

Os identificadores devem ser sempre escritos em inglês.

Exemplo:

```python
user_name
object_found
found_date
pickup_date
central_place
```

Não devemos misturar idiomas:

```text
user
usuario

object
objeto

location
local

category
categoria
```

Devemos escolher uma única convenção:

```text
user
object
location
category
characteristic
photo
pickup
```

# 4. Banco de dados

O banco também deve seguir a padronização em inglês.

As tabelas e colunas devem utilizar `snake_case`.

### Tabelas

```text
user
category
location
object_found
characteristic
photo
pickup
```

### Colunas

```text
id_user
id_object
id_category
id_location
found_date
central_place
person_photo
pickup_date
```

### Chaves primárias

Utilizar:

```text
id_<entity>
```

Exemplos:

```text
id_user
id_object
id_category
id_location
```

### Chaves estrangeiras

As chaves estrangeiras devem manter o mesmo padrão da chave primária referenciada.

Exemplo:

```text
object_found.id_user
object_found.id_category
object_found.id_location
```

# 5. Modelagem atual

O sistema é um web app de **Achados e Perdidos** para a faculdade.

O fluxo inicial é:

1. Um aluno encontra um objeto perdido.
2. O aluno realiza o cadastro do objeto.
3. O objeto fica disponível na listagem pública.
4. Pessoas que perderam objetos podem pesquisar sem autenticação.
5. O objeto possui categoria, características, localização, foto e status.
6. Quando o objeto é retirado, o processo administrativo registra quem realizou a retirada.
7. A retirada registra os dados da pessoa e uma foto para fins de controle e auditoria.

O **RBAC** está previsto para o projeto, mas está **fora do escopo atual**.

---

# 6. Entidades atuais

## User

Representa o aluno que encontrou e cadastrou o objeto.

Campos principais:

```text
id_user
name
cpf
phone
email
rgm
```

O `rgm` representa a matrícula do aluno na faculdade.

---

## Category

Representa o tipo do objeto.

Exemplos:

```text
Cell Phone
Wallet
Keys
Backpack
Documents
School Material
```

---

## Location

Representa o local onde o objeto foi encontrado.

Como a faculdade possui uma estrutura física grande, não queremos criar uma tabela rígida para cada sala ou corredor.

A entidade possui:

```text
id_location
central_place
description
```

Exemplo:

```text
central_place: Block A
description: Corridor in front of room 4
```

Outro exemplo:

```text
central_place: Cafeteria
description: Next to Lab 5
```

`central_place` fornece uma referência geral e `description` permite que o usuário informe detalhes específicos.

---

# 7. Object Found

`object_found` é a entidade central do sistema.

Ela representa o objeto encontrado que foi cadastrado.

Campos atuais:

```text
id_object
id_user
id_category
id_location
status
found_date
```

Relacionamentos:

```text
User 1 ─── N ObjectFound
Category 1 ─── N ObjectFound
Location 1 ─── N ObjectFound

ObjectFound 1 ─── 1 Characteristic
ObjectFound 1 ─── 1 Photo
ObjectFound 1 ─── 0..1 Pickup
```

---

# 8. Characteristic

Armazena as informações descritivas do objeto.

Campos atuais:

```text
id_characteristic
id_object
color
brand
description
```

No estado atual do projeto, os campos descritivos do cadastro são considerados obrigatórios.

A obrigatoriedade de `brand`, entretanto, deve ser revisada durante a evolução do modelo, pois existem objetos cuja marca pode não ser conhecida ou nem sequer existir.

---

# 9. Photo

Armazena a foto do objeto encontrado.

Devido à limitação de infraestrutura e armazenamento, a regra atual é:

```text
1 ObjectFound = 1 Photo
```

Portanto, a relação é um-para-um.

A foto deve armazenar uma referência ao arquivo, e não necessariamente os dados binários diretamente no banco.

Exemplo:

```text
source
```

pode armazenar uma URL, caminho ou identificador utilizado pelo sistema de armazenamento.

---

# 10. Pickup

`pickup` representa o registro administrativo da retirada do objeto.

Essa informação não deve ser confundida com `user`.

A pessoa que retira o objeto não precisa necessariamente ser um usuário cadastrado no sistema.

Dados atuais:

```text
id_pickup
id_object
name
cpf
rg
rgm
phone
person_photo
pickup_date
```

A foto da pessoa é armazenada como evidência do processo de retirada.

Regra atual:

```text
1 ObjectFound = 0..1 Pickup
```

Um objeto pode estar disponível e ainda não possuir uma retirada.

Após a devolução, deve existir um registro de `pickup`.

---

# 11. Status do objeto

Os objetos possuem status.

Inicialmente o status pode ser representado por um campo:

```text
status
```

Exemplo:

```text
AVAILABLE
RETURNED
```

A transformação de `status` em uma entidade/tabela própria pode ser avaliada posteriormente.

Não devemos criar uma tabela para `status` apenas por antecipação. A estrutura deve evoluir conforme uma necessidade real do sistema.

---

# 12. Normalização

O banco deve ser desenvolvido considerando:

* 1ª Forma Normal (1FN);
* 2ª Forma Normal (2FN);
* 3ª Forma Normal (3FN).

Devemos evitar:

* dados duplicados;
* atributos que armazenem múltiplos valores independentes;
* informações que pertencem a outra entidade;
* dependências desnecessárias;
* repetição de dados entre tabelas.

Sempre que uma informação representar uma entidade ou relacionamento independente, devemos avaliar se ela deve possuir sua própria estrutura.

---

# 13. Migration-Oriented Development

A evolução do banco deve seguir uma abordagem baseada em **migrations**.

Cada alteração estrutural importante deve ser registrada como uma nova migration.

Exemplo:

```text
001_create_user
002_create_category
003_create_location
004_create_object_found
005_create_characteristic
006_create_photo
007_create_pickup
```

Caso uma nova necessidade apareça:

```text
008_create_object_status
009_add_pickup_notes
010_update_location_structure
```

Uma migration já executada não deve ser alterada arbitrariamente.

A sequência de migrations deve representar a evolução histórica do banco.

---

# 14. DBML

O DBML será utilizado durante a modelagem para facilitar a visualização do banco no `dbdiagram.io`.

Exemplo:

```dbml
Table object_found {
  id_object int [pk, increment]
  id_user int [not null]
  id_category int [not null]
  id_location int [not null]

  status varchar(30) [not null]
  found_date date [not null]
}
```

Relacionamentos devem ser explícitos:

```dbml
Ref: user.id_user < object_found.id_user
Ref: category.id_category < object_found.id_category
Ref: location.id_location < object_found.id_location
```

O DBML deve acompanhar a evolução do modelo e não deve ser tratado como algo separado da estrutura real do banco.

# 16. Regra geral para novos desenvolvedores

Antes de criar uma nova estrutura no projeto, verifique:

1. O nome está em inglês?
2. A convenção de nomenclatura está correta?
3. A estrutura já existe em outro lugar?
4. Essa informação pertence realmente a essa entidade?
5. A alteração afeta o banco?
6. Se afetar o banco, deve ser criada uma migration?
7. A alteração mantém a normalização do banco?
8. O DBML precisa ser atualizado?

O objetivo é manter o projeto simples, consistente e fácil de evoluir sem criar inconsistências entre o código, o banco de dados e a documentação.
